# Переход к отдельным аккаунтам

## Статус v0.1
Работающее приложение хранит данные только в localStorage, под одним ключом на браузер. Это не авторизация, не шифрование, не многопользовательская изоляция и не синхронизация. Приватный доступ к публикации Sites ограничивает аудиторию страницы, но не превращает локальное хранилище в аккаунт. Другой человек за тем же браузером увидит те же данные. UI сообщает это на входе и в настройках.

`schema.sql` — подготовленная серверная схема, пока НЕ применяется к опубликованной версии. Она проверена на SQLite: составные внешние ключи запрещают ссылку на направление и привычку другого владельца. Они не заменяют авторизацию запросов.

## Серверная граница
Маршрут ИИ уже перенесён в Sites Worker. Для пользовательских записей следующим этапом нужно добавить серверное хранилище. В production доверять идентичности из платформенного middleware, которое проверяет сессию; не допускать прямого доступа к Worker в обход этой границы. Отсутствующая идентичность даёт 401. Заголовки идентичности от обычного браузера вне доверенного gateway не считать доказательством входа. В local preview сервер должен отказывать по умолчанию, а не принимать поддельный user ID.

На каждом запросе сервер получает ownerId из проверенной сессии. В теле, URL или клиентском профиле ownerId не принимается. Все операции, включая list/update/delete/export/photo/chat, используют WHERE owner_id = ? AND id = ?. Запись чужого владельца возвращает 404. Проверку делать до обращения к ИИ или хранилищу фотографий. У клиента никогда нет прямого доступа к БД или ключу ИИ. Ограничить размер входных данных, частоту запросов, расходы ИИ; журналировать коды ошибок без текста личных разговоров. Персональные ответы: Cache-Control private, no-store, без общего CDN-кэша.

## Контракт API
- GET /api/me — текущий профиль из сессии.
- GET/POST /api/directions, /api/tasks, /api/habits — только записи владельца.
- PATCH/DELETE /api/{entity}/:id — owner-scoped mutation; optimistic revision для конфликтов.
- PUT/DELETE /api/habits/:id/marks/:date — одна отметка на локальную календарную дату.
- POST /api/photos — проверить размер, MIME, содержимое; убрать EXIF, хранить объект приватно.
- GET /api/photos/:id — проверить владельца перед stream или краткоживущей подписанной ссылкой; никаких публичных bucket URL.
- POST /api/chat — отдельное согласие на передачу разрешённого контекста провайдеру, ограниченный контекст текущего владельца.
- GET /api/export и DELETE /api/me/data — полная выгрузка / удаление, включая фотографии и разговоры.

Для cookie-сессий: Secure, HttpOnly, SameSite, защита CSRF и проверка Origin на изменяющих запросах; запрещён wildcard CORS с credentials. Секреты только в server environment. Выход очищает клиентский кэш текущего пользователя. Не переключать владельца поверх загруженных данных.

## Персональная память и ИИ
У пользователя всегда виден список разрешённых полей: выбранное «зачем», цели, стиль и явно сохранённая память. Разговоры не создают постоянную память автоматически. Память редактируется и удаляется. Нажатие кнопки разговора, поддержки или разбора еды отправляет соответствующий текст ИИ. Галочка памяти отдельно управляет передачей сохранённых заметок. Интерфейс сообщает об этой передаче. После удаления память не должна оставаться в кэше или формировании следующего контекста. Текст пользователя — данные, а не разрешение обращаться к чужим записям. Модель не должна получать инструменты с неограниченным доступом к БД.

## Приёмка перед приглашением других людей
1. Пользователи A и B имеют разные записи; все CRUD и export тестируются обоими.
2. B не может читать/изменить/удалить данные A при подмене любого ID, ownerId, ссылки фото, conversationId.
3. Анонимный запрос, поддельная сессия, прямой Worker URL и CSRF-запрос отвергаются.
4. Составные связи не разрешают смешивать владельцев, даты привычек уникальны.
5. Выход и смена аккаунта очищают клиентские данные; shared cache не выдаёт чужую информацию.
6. Память выключена — её текст отсутствует в запросе провайдеру; удаление удаляет и серверные объекты.
7. Импорт локальных данных проводится только по явному выбору после входа. Не отправлять их автоматически при открытии сайта.

Этот документ и схема — основа реализации, а не сертификат безопасности. Вход Sites и серверный маршрут ИИ подключены, а также базовое ограничение частоты запросов. Полноценное серверное хранение пользовательских данных, D1/R2 и проверки изоляции двух аккаунтов ещё не подключены.
